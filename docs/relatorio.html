1. Arquitetura

Há um único grupo de servidores, todos mantendo a mesma partida. Os servidores são processos iguais, diferenciados apenas pelo UID recebido como argumento. O papel de líder não é configurado: cada servidor o calcula a partir da sua lista de servidores vivos.

Todos usam um socket UDP ligado à porta 10000 e inscrito no grupo multicast 224.3.29.71 (IP_ADD_MEMBERSHIP). A opção SO_REUSEADDR permite rodar vários servidores na mesma máquina.

Cada servidor tem estas threads:

  • background: envia o heartbeat, remove servidores expirados e recalcula o líder.
  • foreground: escuta a rede e encaminha cada mensagem recebida.
  • trata_move: uma thread criada para cada lance recebido pelo líder.
  • Thread principal: apenas mantém o processo ativo até o Ctrl+C.

O lance roda em thread própria porque o líder precisa esperar ACKs, e esses ACKs chegam pela thread foreground. Esperar dentro dela causaria um deadlock.

2. Protocolo

As mensagens do xadrez são texto no formato TIPO|campo1|campo2. O separador é | porque o FEN contém espaços. O heartbeat tem formato próprio e não faz parte desse conjunto de tipos.

MensagemOrigem → destinoTransporteFormato
Heartbeatservidor → grupomulticastEstou vivo e sou <UID>
READcliente → grupomulticastREAD
MOVEcliente → grupomulticastMOVE|e2e4
SYNClíder → grupomulticastSYNC|seq|uid_lider|fen
ACKréplica → grupomulticastACK|seq|uid
STATElíder → clienteunicastSTATE|fen|situacao
OKlíder → clienteunicastOK|fen|situacao
ERROlíder → clienteunicastERRO|motivo

O cliente envia para o grupo sem saber quem é o líder, com TTL 1. Só o líder responde a READ e MOVE; as outras réplicas ignoram essas mensagens. Os dois programas leem até 1024 bytes por datagrama.

Fluxo de um lance

Cliente             Líder                  Réplicas
   | MOVE|e2e4        |                       |
   |----------------->| valida e aplica       |
   |                  | SYNC|seq|uid|fen      |
   |                  |---------------------->| aplicam o FEN
   |                  |     ACK|seq|uid       |
   |                  |<----------------------|
   |                  | espera até 1 s        |
   | OK|fen|situacao  |                       |
   |<-----------------|                       |
   | READ             |                       |
   |----------------->|                       |
   | STATE|fen|situacao                       |
   |<-----------------|                       |

O ACK é enviado por multicast porque, em localhost, todos os servidores usam a mesma porta, e um unicast poderia chegar ao servidor errado. As notas do grupo registram essa escolha como provisória.

3. Heartbeat

A cada 1 segundo, a thread background registra o próprio servidor como visto, remove quem expirou, envia Estou vivo e sou <UID> ao grupo e recalcula o líder.

O dicionário servidores_vivos guarda, para cada UID, a hora do último heartbeat. Um servidor é removido quando passa mais de 3 segundos sem dar sinal. Como essa verificação ocorre uma vez por segundo, a detecção leva entre 3 e cerca de 4 segundos. Se o servidor voltar a enviar heartbeats, ele é novamente incluído.

4. Eleição

O líder é o menor UID presente em servidores_vivos (função elege_lider). Não há troca de mensagens de eleição: cada servidor chega ao resultado sozinho, a partir da sua própria lista. O cálculo é refeito a cada ciclo de heartbeat e a cada mensagem de xadrez recebida.

Consequências dessa abordagem, observadas no código:

  • Na inicialização ou durante uma falha, listas diferentes podem levar servidores a conclusões diferentes por alguns instantes. Um servidor recém-iniciado, por exemplo, pode se considerar líder até ouvir os demais.
  • Um servidor com UID menor que retorna reassume a liderança assim que é visto de novo.
  • O valor 100000 é usado como limite na busca, então UIDs a partir dele não são eleitos.

5. Tratamento de falhas

SituaçãoComportamento implementado
Líder para de responderOs demais o removem por timeout e o próximo menor UID assume, com o tabuleiro recebido no último SYNC.
Réplica não confirma o SYNCO líder espera até 1 s (TIMEOUT_ACK), registra [AVISO] Sem ACK e responde OK ao cliente mesmo assim.
Nenhuma resposta ao READO cliente espera 2 s, informa o timeout e pergunta se deve tentar de novo.
Nenhuma resposta ao MOVEO cliente espera 2 s, informa o timeout e volta a consultar o tabuleiro. O lance não é reenviado automaticamente.
Mensagem de xadrez inválidaO erro é capturado e registrado, e a thread foreground continua executando.
Lance ilegal ou malformadoO líder responde ERRO|Lance inválido: ... sem alterar o tabuleiro.

Limitações conhecidas

Estas limitações foram identificadas pela leitura do código e não foram medidas em execução:

  • Sem transferência de estado: um servidor que entra ou reinicia começa com o tabuleiro inicial até receber um SYNC. Se ele tiver o menor UID, torna-se líder com esse tabuleiro, e a partida em andamento se perde.
  • Sem quórum: o OK é enviado mesmo sem todos os ACKs, e o SYNC não é reenviado. Como o SYNC leva o FEN completo, uma réplica atrasada só se atualiza no próximo lance.
  • Janela de indisponibilidade: até a detecção da falha, os outros servidores ainda consideram o líder antigo vivo e não respondem ao cliente.
  • Datagramas fora do formato: a decodificação do texto e a leitura do UID do heartbeat ficam fora do try. Um datagrama que falhe nesses pontos encerra a thread foreground daquele servidor.
  • Sem deduplicação de lances: se a resposta ao MOVE se perder depois de o lance ser aplicado, o cliente só descobre o resultado ao consultar o tabuleiro.

6. Serviço de xadrez

O estado da partida é um chess.Board da biblioteca python-chess, mantido em cada servidor. A replicação envia o tabuleiro inteiro em FEN, e não os lances individuais. O número seq identifica cada escrita para associar os ACKs ao SYNC atual.

O cliente repete este ciclo: envia READ, mostra o tabuleiro e a situação, lê um lance e envia MOVE. O ciclo termina quando a partida acaba ou quando o usuário digita sair.

O líder valida o lance com chess.Move.from_uci e board.legal_moves. O texto de situação informa de quem é a vez, xeque, xeque-mate, empate por afogamento, empate por material insuficiente ou outro fim de jogo com o resultado.

O cliente controla os dois lados. A função lance_adversario existe como ponto de extensão, mas retorna None, então não há resposta automática da máquina.
